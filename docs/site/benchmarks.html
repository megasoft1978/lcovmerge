Primary host results

Generated inputs: XXL, S, M, L, XL-single, PATH-HEAVY. Measured lcovmerge build: lcovmerge 1.0.2. Comparators: lcov 2.6 and lcov-result-merger 6.0.0. The release is v1.0.2. Generated measurements do not establish a universal speedup or output compatibility. The REAL dataset was not measured because no project-derived capture was supplied. Windows is verified in GitHub-hosted windows-latest CI: both the MSYS2 UCRT64 GCC build and shipped Zig binary pass the full suite and smoke tests, and separate generated-input benchmark runs are recorded; physical desktops, other Windows versions and real-user reports remain unverified, Windows CI runs no LCOV comparator, and large-dataset timings are disk-bound CI numbers.

Real public CI compatibility notes

On 2026-10-11, lcovmerge 1.0.2 reran three public CI sets (66 shards, 658 MB total). Strict LCOV 2.6 lcov -a failed 3/3; lcovmerge 1.0.2 completed 3/3, with 12 joined-boundary recovery warnings on one set. The original lcovmerge 1.0.1 run found the joined-boundary bug; the affected set's earlier 7 DA, 18 FN, and 18 FNDA differences are gone against diagnostic LCOV. Across all sets, normalized comparisons show 86 lcovmerge-only SF, 713 LCOV-only DA, 2 lcovmerge-only FN, 0 FNDA differences, and 9,877 BRDA key/value differences. The earlier investigation root-caused these classes to documented policies: LCOV's branch-only DA synthesis, empty SF handling, BRDA block-ID remapping, and duplicate legacy FN handling. The rerun compared normalized SF keys and keyed DA, FN, FNDA, and BRDA values/counts; it did not make strict LCOV succeed, did not compare byte-for-byte, did not cover summary, testcase, extension, or other unlisted record families, and did not newly isolate causes. This is compatibility evidence, not proof of equivalence or a performance result.

Method and caveats

Primary host: macOS 27.0 arm64 · Apple M5 Max · 18 cores · 64 GiB RAM; measured 2026-10-11. lcovmerge run counts: S: 10, M: 5, L: 2, XL-single: 5, PATH-HEAVY: 5, REAL: 0. Each row lists its measured tools, run counts, and memory source. Cache conditions: no explicit cache flush; paired hyperfine warmups; machine load uncontrolled Open the published benchmark record.

  • Measurements cover one macOS 27 arm64 Apple M5 Max host; results are not a cross-platform claim.
  • S, M, L, XL-single, and PATH-HEAVY are generated fixtures. REAL was not measured because no project-derived capture was available.
  • lcovmerge baseline and final times use paired hyperfine runs on the same deterministic fixture; run counts are listed per workload. Cache warmups were used, but no explicit cache flush was applied.
  • lcov 2.6 ran once per dataset after the baseline merge. Its PATH-HEAVY run exited with status 1 after 1m 38.8s; no valid speedup or current-run peak resident memory is reported for that failure.
  • The XXL lcov comparator time and peak resident memory were measured in the 2026-10-11 rerun; successful lcov memory figures for earlier datasets remain from the earlier recorded benchmark.
  • lcov-result-merger was not measured in the XXL rerun; earlier datasets retain their separately recorded measurements.
  • Dataset M's sorted regular inputs use one merge worker; --jobs results show run variation, not the effect of adding workers.
  • The external Bazel issue is context only and was not measured with these commands.
