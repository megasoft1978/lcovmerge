Command-line reference

Usage and options

Merge LCOV tracefiles from local builds, test shards or another coverage pipeline. Run lcovmerge --help against the binary you installed for the complete release-specific help text.

Basic syntax

lcovmerge [options] a.info b.info ... -o out.info

The -o or --output option is required. Use - once as an input path to read standard input, or as the output path to write standard output. Prefix an input list with @ to read paths from a list file.

lcovmerge shard-a.info shard-b.info -o merged.info
lcovmerge --mem-limit SIZE --tmpdir "$RUNNER_TEMP" @coverage-files.txt -o merged.info
cat coverage.info | lcovmerge - -o - > normalized.info

List files contain one path per line; blank lines and lines beginning with # are ignored. Nested list files are limited to eight levels, paths are relative to the current working directory, and @@name names a literal path beginning with @. The shell expands globs; lcovmerge does not.

Options

CLI options in lcovmerge 1.0.0
OptionPurpose
-o, --output FILERequired. Write to FILE, replacing it only after a successful merge. Use - for standard output.
--mem-limit SIZESet the record-arena cap; default 64M, minimum 8M per job. Bare values are bytes; case-insensitive K, M, and G suffixes are binary multiples of 1024.
--tmpdir DIRPlace temporary sorted runs in DIR. The default is the system temporary directory.
-j, --jobs NUse 1–32 external-sort jobs. The default is min(4, detected cores), reduced if needed to fit the memory limit; explicit jobs require at least 8M per job. Sorted regular files use a single-threaded stream merge; out-of-order, non-regular, or stream-memory-limited inputs use the configured jobs.
--prefix-strip PREFIXRemove a matching leading SF: path prefix at a path boundary, including separators immediately after the prefix.
--rebase OLD=NEWRewrite a matching leading SF: path prefix. Repeatable; path-boundary matching applies, and directory separator style is preserved where possible.
--include GLOBKeep a path matching at least one include pattern. Repeatable; supports *, ?, and bracket ranges.
--exclude GLOBDrop matching paths. Repeatable; exclusions take precedence over includes.
--branch-coverage on|offKeep or drop BRDA: rows. The default is on; this does not create absent branch data.
--no-function-dataDrop FN, FNDA, FNL, and FNA records.
--strict-checksumReturn status 2 when non-empty checksums for the same source line differ. By default, warn and emit the lexicographically smallest non-empty checksum.
--warn-unknownPrint a diagnostic for every preserved unknown colon-delimited row inside a source section.
-qSuppress routine progress output; errors remain visible.
-vPrint parsed byte and record totals, selected worker count, and merged summary totals to standard error.
--statsPrint merged LF, LH, FNF, FNH, BRF, and BRH totals to standard error.
--versionPrint the version and build's Git commit identifier.
-h, --helpPrint the built-in usage summary.

Path rewriting runs in this order: --rebase, --prefix-strip, then include and exclude filtering. Rewritten paths that become identical are merged.

Exit codes

CodeMeaning
0Success.
1Invalid or incomplete command-line options.
2Input or tracefile format error, including strict checksum disagreement.
3Input/output or temporary-file I/O failure, allocation failure, or interruption.

Rebase source paths

Use a path rebase when reports contain build-agent paths but your checkout uses a different root. The rewrite applies to source file paths carried by SF: records.

lcovmerge --rebase /build/worker/project=/workspace/project shard-a.info shard-b.info -o merged.info

For example, a source path below /build/worker/project is rewritten below /workspace/project. Verify the output paths against the source tree used by your report generator.

Bazel pipelines

Bazel’s coverage tooling can produce or combine LCOV data as part of its own workflow. lcovmerge is a separate tracefile-merging step for pipelines that collect LCOV shard files; it is not a drop-in implementation of Bazel’s CoverageOutputGenerator.

# After a workflow has collected per-target or per-job LCOV files:
lcovmerge @coverage-files.txt -o coverage/merged.info

Point your report generator at coverage/merged.info. The Bazel project has documented memory pressure in its coverage output generator; see issue #26383 ↗.

GitHub Actions with sharded tests

Upload each shard’s LCOV file as an artifact, then download those artifacts in a final merge job. The reusable action downloads and verifies the selected release binary.

jobs:
  tests:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [a, b]
    steps:
      # Replace this with your sharded test command.
      - run: ./run-coverage-tests.sh "${{ matrix.shard }}"
      - run: mv coverage.info "coverage-${{ matrix.shard }}.info"
      - uses: actions/upload-artifact@v7
        with:
          name: coverage-${{ matrix.shard }}
          path: coverage-${{ matrix.shard }}.info

  merge:
    needs: tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v8
        with:
          pattern: coverage-*
          path: coverage-shards
          merge-multiple: true
      - uses: megasoft1978/lcovmerge@v1
        with:
          files: coverage-shards/*.info
          output: coverage/merged.info
          mem-limit: 256M
      - run: genhtml coverage/merged.info --output-directory coverage/html

This example uses current GitHub artifact actions. Keep each shard tracefile name unique so a flat artifact merge cannot overwrite a file with the same name.

GitLab CI

Have each test job publish a distinct LCOV artifact. In the merge job, download those artifacts, install the release archive for the runner, and keep the merged file as the handoff to your report step.

mkdir -p coverage
./lcovmerge coverage/*.info -o coverage/merged.info
genhtml coverage/merged.info --output-directory coverage/html

Verify the archive with SHA256SUMS before installation. GitLab’s built-in coverage visualization accepts Cobertura or JaCoCo, not LCOV; retain the merged .info for an LCOV-aware uploader or convert it separately. See the full GitLab example ↗.

CMake and gcov

Compile and run tests with gcov instrumentation, capture LCOV, then merge the files produced by independent shards.

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_FLAGS=--coverage -DCMAKE_CXX_FLAGS=--coverage
cmake --build build
ctest --test-dir build --output-on-failure
mkdir -p coverage
lcov --capture --directory build --output-file coverage/shard-1.info
# Repeat in each CI shard with a distinct output path
lcovmerge coverage/shard-*.info -o coverage/merged.info

See the full CMake recipe ↗ for gcovr and build-tree notes.

Report and upload consumers

The merged file remains LCOV. Pass it to genhtml, Codecov, or a Coveralls integration that accepts LCOV. SonarQube accepts LCOV for analyzers including JavaScript/TypeScript, Dart, and Rust; its C/C++ analyzer imports gcov or llvm-cov reports instead. See the consumer notes and references ↗.

Jenkins

Collect LCOV files from parallel stages and merge them after the test stage completes.

find coverage -type f -name '*.info' -print | sort > coverage-files.txt
lcovmerge @coverage-files.txt -o coverage/merged.info

Keep the list file outside the searched output directory if your job runs the collection step more than once.

How it differs from lcov

lcov is a broader Perl coverage tool. It can capture coverage from compiler data, combine tracefiles with --add-tracefile, and filter, extract, summarize and report coverage. lcovmerge focuses on merging existing LCOV tracefiles under a configured memory budget; it does not replace the broader capture and reporting workflow. Recent lcov versions also expose memory and parallel-processing controls, so compare the versions and settings that match your pipeline.

See the lcov manual ↗ and LCOV tracefile documentation ↗. lcovmerge does not claim MC/DC semantic accounting.
