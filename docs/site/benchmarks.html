Methodology

  • Machine, cache state and per-tool run counts are loaded from the benchmark data file.
  • Dataset names, input sizes, shard counts, and descriptions load from the benchmark data file.
  • Measurements: elapsed wall time and peak resident memory.
  • Compared tools load from the benchmark data file.

Reproduction steps

  1. Prepare the input type and tool versions shown in the results table. Use the same input paths for each implementation.
  2. Match the recorded host, cache state, and run counts in the benchmark data file. Keep machine load and output destination consistent.
  3. For lcovmerge, put the input paths in a list file and run:
lcovmerge @paths.txt -o merged.info

lcov combines tracefiles with --add-tracefile; see the lcov manual for its accepted patterns and options. Use each other tool’s documented CLI with the same tracefiles and release shown above.

  • On macOS, /usr/bin/time -l reports elapsed time and maximum resident set size.
  • On Linux, /usr/bin/time -v reports elapsed time and maximum resident set size.
  • Record the exact command, version, host, cache state, elapsed time and peak RSS for any new run.

Caveats

  • Synthetic fixtures do not cover every real project’s path patterns, record mix, checksums or shard layout.
  • Run counts and cache state vary by dataset. Check the recorded method before treating a result as representative; these measurements are not a confidence interval or cross-platform comparison.
  • The tools do different things. lcov has a broader capture, filtering and reporting workflow; lcovmerge focuses on merging existing LCOV tracefiles. Versions, feature settings and command lines affect the result.
  • Rows marked unavailable, timed out, or not measured are not successful timing comparisons.
  • Performance results apply to the host recorded in the data file. Runtime support and performance on other platforms require separate verification.
