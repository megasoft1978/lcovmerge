Why this exists

Keep the merge job from becoming the coverage bottleneck.

Monorepos and test-sharded pipelines combine many tracefiles at the end of a build. Bazel, CMake, and Gradle C++ teams can use lcovmerge when their existing coverage steps already write LCOV.

Large coverage merges can demand more than the runner has.

Bazel issue #26383 reports high heap use in Bazel’s own coverage output generator. That issue is context for the problem; lcovmerge does not change Bazel’s implementation, and the issue’s workload was not part of our benchmark.

Bazel issue #26383 ↗ Review the measured cases ↗

Three reasons to switch the merge step

A smaller, predictable job at the end of CI.

Memory-bounded

Cap record memory.

Stream records and spill sorted runs to temporary disk. --mem-limit caps the record arena; total RSS and disk use are separate.

Deterministic

Get canonical output.

The same inputs and options produce byte-identical output across input order and -j settings.

Fast & portable

Keep the merge lean.

One C11 executable per target, with no Node.js or JVM runtime. Linux builds are static musl; macOS uses the system library; Windows uses Windows APIs.

Memory accounting, platform validation, and semantics are documented in limitations and intentional differences.

Get started

Install the binary or use your CI action.

Choose a release archive, or use the reusable GitHub Action when your shards are workflow artifacts. Release files include checksums; verify the archive before installing.

Linux · static musl binary

For a quick Linux x86-64 install, download the release archive, verify it, and run the binary.

asset=lcovmerge-1.0.0-linux-x86_64.tar.gz
base=https://github.com/megasoft1978/lcovmerge/releases/download/v1.0.0
curl -fL "$base/$asset" -o "$asset"
curl -fL "$base/SHA256SUMS" -o SHA256SUMS
grep " $asset$" SHA256SUMS | sha256sum -c -
tar -xzf "$asset"
./lcovmerge --version

Choose the matching linux-x86_64 or linux-aarch64 archive from the release page ↗.

macOS binary

Download the release archive for your Mac, then verify and unpack it:

set -eu
base=https://github.com/megasoft1978/lcovmerge/releases/download/v1.0.0
case "$(uname -m)" in
  arm64|aarch64) asset=lcovmerge-1.0.0-macos-arm64.tar.gz ;;
  x86_64|amd64) asset=lcovmerge-1.0.0-macos-x86_64.tar.gz ;;
  *) echo "Unsupported Mac architecture: $(uname -m)" >&2; exit 1 ;;
esac
curl -fL "$base/$asset" -o "$asset"
curl -fL "$base/SHA256SUMS" -o SHA256SUMS
grep " $asset$" SHA256SUMS | shasum -a 256 -c -
tar -xzf "$asset"
./lcovmerge --version

Before / after

Change the merge command. Keep the report step.

For a file-only merge stage, replace the merger command and leave your .info consumer in place.

Before · lcov

coverage job · before
lcov -a shard-a.info \
  -a shard-b.info \
  -o coverage/merged.info

After · lcovmerge

coverage job · after
lcovmerge coverage/shard-*.info \
  -o coverage/merged.info

For the same file inputs and output path, this maps the command shape only. Then run genhtml or your uploader as before; output order, summaries, checksums, testcase handling, and MC/DC behavior are not interchangeable. Read the documented differences.

How it works

Read, sort, merge, stream.

Parsing is incremental and --mem-limit caps the record arena. Total RSS and temporary disk use are not fully capped.

Built for coverage pipelines

A focused LCOV merger with CI controls.

  • ✓Bounded-memory processingSet a working memory budget and a temporary directory for the merge.
  • ✓Large input listsRead input paths from an @listfile; use - for standard input or output.
  • ✓Path cleanupRebase source paths or strip a prefix to reconcile build and checkout paths.
  • ✓Record controlsFilter SF: paths, enable or disable branch coverage, and omit function data.
  • ✓Validation signalsChoose strict checksum handling and warnings for unknown records.
  • ✓Portable distributionLinux binaries are static musl, macOS binaries link Apple's libSystem, and Windows statically links runtime libraries while using Windows system APIs.

Limits and compatibility

Know when to keep your existing tool.

Use lcovmerge only when its LCOV semantics fit the report you need. Read the full limitations and intentional differences.

Need exact lcov behavior?

Keep lcov -a when you depend on testcase-aware reporting, lcov-specific configuration, or MC/DC semantics. lcovmerge canonicalizes output and documents semantic differences.

Need raw-data collection or reports?

Keep lcov or grcov for collection and conversion. lcovmerge accepts existing LCOV tracefiles and does not create HTML reports.

Need a total RSS or disk cap?

--mem-limit bounds the record arena, not total RSS. External sorting needs temporary disk space proportional to input and intermediate runs.

Expect one file to use many workers?

Parallel parsing is across input files. One large file does not scale across parser workers, and the merge stage is single-threaded.

FAQ

A few practical details.

Is the output identical to lcov -a?

No. lcovmerge writes canonicalized output and documents semantic differences. Keep lcov when you depend on its behavior. Read the compatibility details ↗

Does lcovmerge replace lcov?

No. It handles LCOV tracefile merging. lcov also captures coverage, filters and extracts tracefiles, summarizes data and supports other coverage workflows. Both tools can merge LCOV tracefiles; see the lcov manual ↗.

Can I feed it coverage shards from CI?

Yes. Pass the shard paths directly, or use @listfile for a long input list. A merge job can combine artifacts after test shards finish. See the GitHub Actions example.

Does it merge MC/DC coverage?

No MC/DC semantic guarantee is made. The published scope covers line, function and optional branch data. Check the current CLI documentation and your compiler and lcov versions before relying on other records.

Where are benchmark inputs and commands?

The benchmark page explains the synthetic inputs, host, run counts, caveats and reproduction procedure. The operating-system cache state was not controlled.
