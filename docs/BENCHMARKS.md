# Benchmarks

[`data/benchmarks.json`](../data/benchmarks.json) is the canonical record for benchmark measurements. The tables in
this file, the README, and the site data are rendered from it.

## Methodology

<!-- BENCH-METHOD:START -->
Host: macOS 27.0 arm64, Apple M5 Max, 18 cores, 64 GiB RAM; uncontrolled; fixtures generated immediately
before measurements. Measured: 2026-10-09. lcovmerge runs by dataset: S: 1, M: 5, L: 1, XL-single: 1,
PATH-HEAVY: 1, REAL: 0. Each comparison tool ran 1 time(s) per dataset. Per-command timeout: 30 minutes.
<!-- BENCH-METHOD:END -->

- Synthetic fixtures were generated by `bench/run.py` using `tools/gen-lcov.py` and `tools/gen-path-heavy.py`.
  The harness uses a temporary directory outside the repository and removes generated inputs after each run.
- Input size is the exact sum of input file bytes. Throughput is input bytes divided by elapsed wall time using
  decimal MB/s. Peak RSS comes from `/usr/bin/time -l` on this host.
- The tool commands return output and exit status; benchmark outputs were not compared pairwise. Semantic behavior
  is checked separately by the golden, oracle, and lcov differential suites.
- `lcov` is invoked with branch coverage enabled and `-a` for every shard. `lcov-result-merger` 6.0.0 is invoked
  with the corresponding input glob. Its PATH-HEAVY case receives a timeout if it does not finish.
- Files are generated immediately before measurements. There is no explicit cache warm-up or cache flush, so the
  operating-system cache state is uncontrolled. Runs are single samples, not a median or confidence interval.

To reproduce the generated workloads from the repository root:

```sh
make
npm install --prefix /tmp/lcovmerge-node lcov-result-merger@6.0.0
python3 bench/run.py --workload S --node-bin /tmp/lcovmerge-node/node_modules/.bin/lcov-result-merger
python3 bench/run.py --workload M --node-bin /tmp/lcovmerge-node/node_modules/.bin/lcov-result-merger
python3 bench/run.py --workload L --node-bin /tmp/lcovmerge-node/node_modules/.bin/lcov-result-merger
python3 bench/run.py --workload XL-single --node-bin /tmp/lcovmerge-node/node_modules/.bin/lcov-result-merger
python3 bench/run.py --workload PATH-HEAVY --node-bin /tmp/lcovmerge-node/node_modules/.bin/lcov-result-merger
```

REAL accepts `--real-dir` pointing at project-derived `.info` captures. No such capture was available in this
repository, so REAL was not measured. The small LCOV files under `tests/fuzz-corpus/` are test fixtures and were
not substituted for project data.

## Caveats

<!-- BENCH-CAVEATS:START -->
- Single-run measurements on one Apple M5 Max host; they are not a median, confidence interval, or
  cross-platform performance claim.
- S, M, L, XL-single, and PATH-HEAVY are generated fixtures. REAL was not measured because no project-derived
  capture was available; only fuzz-corpus test fixtures were present.
- No explicit cache control was applied, and measurements were run in a fixed tool order, so operating-system
  cache state and machine load may affect cross-tool comparisons.
- Benchmark command exit status and resource use were measured; outputs were not compared pairwise. Semantic
  coverage is checked by the golden, oracle, and lcov differential suites.
- Sorted regular input shards use the direct single-threaded path. M job-setting runs therefore record timing
  variation, not external-sort worker scaling.
- lcov exited with an error on PATH-HEAVY after 89.383 s and used 7,037,177,760 B peak RSS; no throughput is
  reported for that failed run.
- lcov-result-merger PATH-HEAVY reached the 1,800 s timeout. /usr/bin/time did not report RSS on forced
  termination; a one-second sample during the final 308.3 s observed 841,888 KiB, which is not a full-run
  peak.
- The external Bazel issue evidence is context and was not measured with these commands.
<!-- BENCH-CAVEATS:END -->

The benchmark set is not a conformance suite. It cannot establish equivalence across every LCOV extension or
project workload. lcovmerge does not implement MC/DC semantics. The [Bazel issue](https://github.com/bazelbuild/bazel/issues/26383)
describes a separate memory-pressure case; it is not a benchmark result for this repository.
