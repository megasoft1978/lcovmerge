LCOV 2.6 merge profile

On 2026-10-14, Rust commit 31be2d8 was measured against pinned LCOV 2.6 XS and pure Perl on an idle four-core Linux Azure runner. Six synthetic workloads cover lines, mixed records, testcases, a large single source, 64 shards, and gzip. Each used 19 paired runs at one and four jobs, with matching normalized output on every invocation.

Rust was faster than pure Perl in these measured cases. XS was faster for mixed records and gzip at both job counts, and for the large single source at four jobs. These results do not establish universal superiority or native-mode parity with the previous implementation.

Real public CI compatibility notes

On 2026-10-11, lcovmerge 1.0.2 reran three public CI sets (66 shards, 658 MB total). Strict LCOV 2.6 lcov -a failed 3/3; lcovmerge 1.0.2 completed 3/3, with 12 joined-boundary recovery warnings on one set. The original lcovmerge 1.0.1 run found the joined-boundary bug; the affected set's earlier 7 DA, 18 FN, and 18 FNDA differences are gone against diagnostic LCOV. Across all sets, normalized comparisons show 86 lcovmerge-only SF, 713 LCOV-only DA, 2 lcovmerge-only FN, 0 FNDA differences, and 9,877 BRDA key/value differences. The earlier investigation root-caused these classes to documented policies: LCOV's branch-only DA synthesis, empty SF handling, BRDA block-ID remapping, and duplicate legacy FN handling. The rerun compared normalized SF keys and keyed DA, FN, FNDA, and BRDA values/counts; it did not make strict LCOV succeed, did not compare byte-for-byte, did not cover summary, testcase, extension, or other unlisted record families, and did not newly isolate causes. This is compatibility evidence, not proof of equivalence or a performance result.

Method and caveats

Primary host: macOS 27.0 arm64 · Apple M5 Max · 18 cores · 64 GiB RAM; measured 2026-10-12. lcovmerge run counts: S: 5, M: 5, L: 5, XL-single: 5, PATH-HEAVY: 5, REAL: 0, XXL: 3. Each row lists its measured tools, run counts, and memory source. Dataset M-trained PGO; portable release binaries. Cache conditions: no explicit cache flush; paired hyperfine warmups; machine load uncontrolled Open the published benchmark record.

  • Measurements cover one macOS 27 arm64 Apple M5 Max host; results are not a cross-platform claim.
  • S, M, L, XL-single, and PATH-HEAVY are generated fixtures. The generated benchmark matrix REAL row remains unmeasured; separate public-project captures and comparisons are recorded in docs/validation/real-projects.md.
  • All displayed lcovmerge measurements use a Dataset M-trained Apple Clang profile-guided host build. Release binaries remain portable target builds; this is not a cross-platform speed claim.
  • lcovmerge timing uses one hyperfine warmup and five measured runs for S, M, L, XL-single, and PATH-HEAVY; XXL uses one warmup and three measured runs. Cache warmups were used, but no explicit cache flush was applied.
  • lcov 2.6 ran once on the XXL input on 2026-10-12 and completed in 13m 47.6s; the 2026-10-11 run recorded 18m 0.6s on the same host with machine load uncontrolled. Its S, M, L, XL-single, and PATH-HEAVY values are earlier recorded measurements that were not rerun; the PATH-HEAVY run exited with status 1 after 1m 38.8s, so no valid speedup or current-run peak resident memory is reported for that failure.
  • lcov-result-merger 6.0.0 did not finish its XXL warmup before the 60-minute cutoff in the 2026-10-11 run and was not rerun for 1.1.0. It was stopped with SIGTERM after 1h 15.8s wall time; no measured run completed. Periodic peak resident memory samples peaked at 2.34 GiB, but the full-run peak is unavailable. Other lcov-result-merger rows are earlier measurements made with Node v24.14.0.
  • Dataset M's sorted regular inputs use one merge worker; --jobs results show run variation, not the effect of adding workers.
  • grcov 0.10.8 is identified as the current release but was not included in the measured benchmark runs.
  • The external Bazel issue is context only and was not measured with these commands.

The largest published result uses generated input. To contribute optional, sanitized results from private captures without uploading coverage data, follow the private-input measurement guide.
